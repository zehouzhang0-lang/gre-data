# 词墙检索：测量与候选优化

2026-11-22。只用合成词库，没有读取真实词库、SQLite、备份或作答记录。**正式代码没有改动**，优化以候选文件和补丁的形式放在本目录，等你点头再接入。

结论：

1. 检索函数本身不是瓶颈。1 万词的合成词库上，原版每次按键约 4 ms（桌面）。
2. 真正的开销在界面层：每按一个键，整页 28 个词块被拆掉重建，而且这件事卡在按键事件里，输入框要等它做完才显示这个字。
3. 候选改动之后，每次按键的阻塞从约 10–15 ms 降到 0.5 ms，连打五个键的总阻塞从 44–71 ms 降到约 3 ms。检索结果与原版逐项相同。

## 现在每按一个键发生什么

读代码得到，行号指 `platform/mobile/src/`。

| 步骤 | 位置 | 做了什么 |
| --- | --- | --- |
| 拼搜索文本 | `model.mjs:45` | 对全库每个词拼接「词 释义 笔记」并转小写，每次按键都重做 |
| 排序 | `model.mjs:52` | 对所有命中的词排序。A–Z 用 `localeCompare(…, 'en')`；随机排序每比较一次算两次哈希 |
| 多余的查找 | `model.mjs:43–44` | 每个词都查主题和排期，不管有没有开对应筛选 |
| 整页重建 | `components/WordWall.jsx:245–246` | 页面的 key 里带着查询词，分区的 key 是第一个词。两者任一变化，28 个词块全部卸载重建，并重放 100 ms 入场动画 |
| 同步执行 | `components/WordWall.jsx:87–89` | 以上全部在按键事件里做完，输入框才更新 |
| 输入法 | `components/WordWall.jsx:235` | 不区分拼音组合中的字母，打「qingxi」会完整检索六次 |

## 测量

### 检索函数

`bench.mjs`，Node 24，同一份合成词库，同一串输入，单位 ms，中位数。

| 词量 | 每次按键 A–Z | 随机排序 | 带记忆状态筛选 | 重建索引 |
| ---: | --- | --- | --- | --- |
| 2,000 | 0.78 → 0.11（6.8 倍） | 0.86 → 0.12 | 0.77 → 0.13 | 1.8 → 1.2 |
| 5,000 | 1.99 → 0.36（5.5 倍） | 2.20 → 0.35 | 1.96 → 0.36 | 4.3 → 3.3 |
| 10,000 | 4.00 → 0.86（4.7 倍） | 6.18 → 1.61 | 6.66 → 1.62 | 17.8 → 10.7 |
| 20,000 | 16.6 → 3.65（4.6 倍） | 18.3 → 3.93 | 16.7 → 3.86 | 38.3 → 27.0 |

候选版有一次性的代价：词库里增删了词之后，第一次检索要重新排一次序（1 万词约 16 ms，原版单次约 7 ms），之后每次按键都省。只是改了标记或释义、词没有增删时不用重排（1 万词约 2.6 ms）。

各次运行之间有 20% 左右的波动，倍数比毫秒数可靠。原始数据在 `BENCH.json`。

### 词墙组件

`ui-bench.mjs`，无头 Chrome 158，390×844，把正式的 `WordWall.jsx` 和候选版分别挂在合成词库上，输入同一串字符。单位 ms，中位数。

| 词量 | 按键被阻塞 | 词墙更新完成 | 加一个字母时重建的词块 | 连打五键的总阻塞 |
| ---: | --- | --- | --- | --- |
| 2,000 | 9.8 → 0.5 | 9.8 → 9.1 | 28 → 2（其中 11 个本来就该留着） | 44.1 → 2.4 |
| 5,000 | 11.4 → 0.5 | 11.4 → 10.1 | 28 → 9（12 个该留着） | 55.4 → 2.8 |
| 10,000 | 15.0 → 0.5 | 15.0 → 10.8 | 28 → 13（7 个该留着） | 70.6 → 2.9 |

- 「按键被阻塞」是按键事件本身运行的时间。这段时间里输入框不更新，下一个键也进不来。
- 「词墙更新完成」是从按键到词墙最后一次变化。
- 两版在每一步显示的词完全相同；快速连打时输入框始终显示最新输入，不回退。

**这些数字的边界**：这是桌面 CPU 加开发模式的 React，比正式构建慢好几倍，手机又比桌面慢好几倍，两个方向都不能直接换算。能确定的是两版之间的比例，以及「按键不再等结果」这个性质。真机上的绝对数字需要在手机上测。

## 候选改了什么

| 改动 | 作用 | 所在 |
| --- | --- | --- |
| 全库顺序只算一次 | 每种排序（随机排序每个种子）算一次并记住，只要词的名单没变就一直有效。按键时只沿这个顺序走一遍、留下命中的，不再排序 | `fast-filter.mjs` |
| 搜索文本只算一次 | 每个词的小写「词 释义 笔记」算一次，词条对象被替换时自动重算 | `fast-filter.mjs` |
| 条目对象复用 | 同一个词每次返回同一个条目对象，`WordTile` 的 memo 才能生效 | `fast-filter.mjs` |
| 页面和分区的 key 不再跟着查询词变 | 还在屏幕上的词块原样保留，只新建新出现的词 | 补丁，`WordWall.jsx` |
| 输入框自己保存文字，检索作为 transition 提交 | 按键立刻显示；结果稍后跟上，下一个键到来时 React 可以丢弃没算完的那次 | 补丁，`WordWall.jsx` |
| 输入法组合期间不检索 | 拼音字母不再触发检索和「没有匹配」的闪现 | 补丁，`WordWall.jsx` |
| 来源标签记住结果 | `buildIndexes` 每次保存后都会跑，原来对每个词的每个来源都做一遍正则 | `fast-filter.mjs` |

## 结果为什么不变

- 原版先按词库顺序筛选，再做稳定排序。候选版先对全库做稳定排序，再筛选。任意两个词的先后在两种做法下相同，包括排序键相等的词。
- 小写搜索文本用的是原版同一个表达式。
- 分组视图（按关系排列）的代码原样照搬。
- `equivalence.test.mjs` 做了约 2,400 组随机筛选条件（查询、排序、种子、主题、来源、记忆状态、首字母、范围、关系、指定组的各种组合）、逐字输入、以及词库被替换后（保存标记、增词、删词、改释义、调换顺序）的对比，全部与原版 `deepStrictEqual`。7 项通过。
- 项目自带的 `wall-model`、`wall-navigation`、`curation` 三组测试共 23 项，在未改动的正式代码上仍然通过。

候选版依赖一个前提：有变化时 App 会替换 `state.vocabulary` 和其中的词条对象，而不是原地修改。`WordWall.jsx` 自己的 `useMemo` 已经依赖同一个前提。

顺带发现一处原版行为，候选版原样保留了：没有释义的词，搜索文本里会出现字面的 `undefined`，所以搜「und」会命中它们（`model.mjs:45` 直接把 `w.meaning` 拼进模板字符串）。建议另开一处修掉，不混进这次性能改动。

## 接入正式代码的步骤

没有执行，等你确认。

1. 把 `fast-filter.mjs` 复制为 `platform/mobile/src/wall-search.mjs`，把里面的 `'../../src/model.mjs'` 改成 `'./model.mjs'`。
2. 在仓库根目录执行 `git apply platform/mobile/ui-redesign/search/production.patch`。
3. 把 `equivalence.test.mjs` 和 `synthetic-state.mjs` 移进 `platform/mobile/tests/` 并改好引用路径，让它随 `npm test` 一起跑。
4. 跑 `npm test`，再做一次正式构建。

涉及的文件只有 `src/wall-search.mjs`（新增）和 `src/components/WordWall.jsx`（4 处）。不动 `model.mjs`、repository、事件模型、Fresh、复习轮次和题库。

回归要看的：

- 相同筛选下词的数量、顺序、分组与改动前一致。
- 搜索中翻页、清空后回到搜索前的位置。
- 搜索时词块不再整页闪动；翻页和 Fresh 的入场动画仍在。
- 保存标记后已标记的词仍留在原位（原版的既有规则）。
- 增删词后排序正确。
- 中文输入法：打拼音时不检索，选字后检索一次。

真机待测：

- 真实词量下的按键延迟和掉帧，用正式构建测。
- 中文输入法的组合事件在 Android WebView 里的实际顺序。
- 快速输入时输入框是否跟手。

撤回：`git checkout -- platform/mobile/src/components/WordWall.jsx`，删掉 `src/wall-search.mjs`。不涉及任何数据。

## 没有做的

- 没有改检索的语义：不加拼写容错、不改排序规则、不做相关度排名。
- 没有处理分组视图的开销，那条路径原样保留。
- 不知道你真实的词量。如果远超 2 万词，值得再做一步：查询只是在上一次基础上多打了一个字时，只在上一次的结果里筛。现在的规模下这一步省不出可感知的时间，所以没加。
